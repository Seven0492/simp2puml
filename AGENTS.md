# Consignes pour les agents

## Architecture et API
- Le paquet installable réside dans `src/simp2puml/` : `model.py` définit le modèle commun et ses invariants ; `cli.py` orchestre la CLI ; `puml.py` et `simp.py` sont des implémentations disjointes des deux formats ; `atelier.py` est un export en écriture seule vers le DSL 2.0 d’Atelier Diagrammes (`write_atelier`, qui ajoute ses pertes détectées à `UMLDiagram.warnings`). API directe : `from simp2puml.puml import parse_puml, write_puml` et `from simp2puml.simp import parse_simp, write_simp`. `parse_simp(text, diagram=None)` ; les erreurs sont `ConversionError` (`simp2puml.model`) et les avertissements/pertes détectées figurent dans `UMLDiagram.warnings`.
- `gui.py` est une interface Tkinter (`simp2puml-gui`, `python -m simp2puml.gui`) ; elle passe par `cli.convert`, `cli.summary_lines` et les helpers de lecture/publication de `cli.py`, sans logique de conversion propre. Ses fonctions `run`/`save` sont testables sans affichage ; les icônes de `assets/` (La Joconde, domaine public) sont générées par `tools/build-icons.py`, ne pas les retoucher à la main ; garder ses garde-fous alignés sur la CLI (strict, refus d’écrasement, reconversion avant publication).
- `render.py` : moteur natif PlantUML préféré (archives et sommes dans `NATIVE_BUILDS`, même version que le jar), repli Java + jar. L’aperçu passe par `PreviewRenderer` (processus `-pipe -pipeNoStderr` ouverts, SVG pour la taille, PNG avec `skinparam dpi` injecté et numéros de ligne d’erreur corrigés) ; `render()` ponctuel pour les exports et les tests. Ne pas lire de variable Tk depuis un fil de travail ; les tâches de fond ne capturent que les files de messages. En mode `-pipe`, PlantUML numérote les lignes d’erreur à partir de 0 (`_pipe_error` convertit). L’onglet Résultat est éditable : un texte modifié (`_dirty`) remplace la conversion pour l’aperçu, l’export et l’enregistrement (`save_text`, tel quel) ; ne jamais l’écraser sans confirmation.
- Rendu d’images avec profil `SANDBOX` obligatoire (`SECURE` autorise `!include` de .puml locaux), dans un dossier temporaire ; jamais de serveur PlantUML distant. Installation à la demande avec vérification SHA-256 (PlantUML : somme fixée ; Java : API Adoptium) dans le dossier de données partagé avec les lanceurs. Mettre à jour version et somme ensemble.
- `launchers/` : lanceurs à double-cliquer (`simp2puml-windows.cmd`, `simp2puml-macos.command`, `simp2puml-linux.sh` à la racine) ; Python privé via uv si aucun Python ≥ 3.11 avec Tk n’existe, sans droits administrateur. Versions de uv/Python identiques dans `bootstrap.sh` et `bootstrap.ps1` (test). `.sh`/`.command` en LF et exécutables ; `.cmd` en CRLF ; `bootstrap.ps1` en UTF-8 avec BOM (PowerShell 5.1). `SIMP2PUML_NO_SHORTCUTS` et `SIMP2PUML_FORCE_MANAGED` servent aux essais.
- Les points d’entrée sont `simp2puml` et `python -m simp2puml`. `main.py` à la racine reste un wrapper de compatibilité, pas l’implémentation de la CLI. Version : `0.1.0`, définie dans `simp2puml.__init__` et utilisée par le paquet ; ne pas la dupliquer ou inventer d’autres sources de vérité.
- Éditeur : `editor/` (Rust, GPUI 0.2.2 ; `libc` verrouillé à 0.2.186 dans `Cargo.lock` car `xattr` 0.2 ne compile plus avec les versions suivantes) et moteur `renderer/` (Nim ≥ 1.6, binaire `pumlrender` ; l'éditeur utilise `--serve`, protocole lu par `editor/src/model/diagram.rs`). Composants distincts du paquet Python, hors sdist/wheel et hors recettes natives. L'éditeur suit MVVM : `model/` sans GPUI, `services/` pour processus et fichiers, `viewmodel/` pour l'état et les commandes (aucun dessin), `view/` pour le dessin et les entrées (dialogues et focus y restent, déclenchés par des évènements de ViewModel). Ne pas mélanger ces couches. Couleurs : uniquement via `view/theme.rs` (palettes claire et sombre choisies à chaque rendu par `WorkspaceView` d'après `model/preferences.rs`) ; aucune couleur codée en dur dans les vues ; les couleurs du diagramme passent par `theme::diagram`. L'aperçu est vectoriel (`model/svg_scene.rs` + `view/preview_view.rs`) : ne pas réintroduire de rastérisation ; tout nouvel élément SVG émis par `pumlrender` doit être pris en charge par `svg_scene.rs`. Le rendu natif ne vise pas l'identité avec PlantUML et n'exécute jamais le préprocesseur. Les passes de mise en page du moteur sont récursives : toute nouvelle imbrication passe par `MaxNesting`/`tooDeep` (`common.nim`), une pile épuisée tuerait le processus sans diagnostic. Tests : `cd renderer && nim c -r --path:src tests/test_render.nim`, `cd editor && cargo test`. Les parcours d'interface sont dans `view/interface_tests.rs` (plateforme de test de GPUI, activée en `dev-dependencies` seulement ; un bouton se retrouve par son identifiant via `debug_bounds`, sans effet sur le binaire publié) : préférer ce moyen à une fenêtre réelle pour vérifier une interaction. Leur dossier de configuration est temporaire, jamais celui de l'utilisateur.
- Responsabilités séparées : modèle commun, orchestration CLI et adaptateurs de formats. Runtime bibliothèque standard, Python ≥ 3.11 ; `pytest` et outils de construction sont des dépendances de développement uniquement. Dépendances de construction/distribution selon `pyproject.toml` et `requirements-dev.txt`.
- Rendu structurel (`simp_puml.py`) : les positions SIMP (`layout` x, y, width, height) donnent la direction de chaque lien (`direction`/`directed`), le côté des notes reliées à un seul élément (`note_side`) et leur largeur de coupe (`wrap_note`). Les symboles d’interface restent au rang voisin (jamais gauche/droite, cela les éloigne). Les colonnes SIMP deviennent des liens `-[hidden]down-` (`columns`), calculées séparément pour les éléments reliés et isolés. `smetana` ignore `together` et `linetype` : ne pas s’y fier. Garder les indications facultatives (`layout_hints`) et valider les sorties avec `PLANTUML_JAR`. Côté interface, `strip_layout_hints` (disposition libre) ne touche que les lignes de relation `E<n>`.
- `simp_document.py` lit et sélectionne toutes les familles XML monofichiers et conserve les occurrences distinctes. `simp_puml.py` exporte les vues enrichies (structures, séquences ou graphe annoté). `UMLDiagram.source_view` est renseigné pour ces vues : les collections historiques `classes`/`relationships` n’en sont pas une projection. `write_puml` choisit l’adaptateur ; `write_simp` et `write_atelier` refusent explicitement ces vues. `list_diagrams(text)` renvoie `(id, name, type)` ; la CLI propose `--list-diagrams` et `--all` (blocs PlantUML séparés, publication unique après toutes les conversions).

## Invariants du modèle
- Identités internes distinctes des noms affichés ; les classes homonymes restent distinctes. `UMLClass.kind` vaut `class`, `interface`, `enumeration` ou `interface_symbol` ; seules les énumérations ont des `literals` ordonnées. Une interface-symbol est un classifieur distinct sans membres ni modificateurs et cible des connecteurs fournis. Notes : identité `id`, texte brut `text`, références `targets`. Ne jamais inventer une identité ou résoudre arbitrairement une référence de type ambiguë.
- Pour l’héritage, `source` est l’enfant et `target` le parent. Les relations normalisées gardent la source à gauche et la cible à droite ; en composition, `source` est le tout. Préserver rôles, visibilités et multiplicités d’extrémité quand présents.

## Fidélité et sécurité
- Le profil SIMP est expérimental. Ne pas déduire la version de l’application de l’XML `12.75`, ni annoncer une compatibilité sans vérification dans l’application cible. La génération de structures/types textuels et `visibility` reste à valider. Ne pas assimiler nombre d’avertissements et nombre d’éléments perdus.
- `Monopoly.simp` à la racine est une fixture réelle protégée : ne jamais la modifier ni la redistribuer. Elle contient une généralisation sans origine, omissible avec avertissement seulement si l’autre extrémité existe, qu’elle n’est référencée nulle part et que le diagramme a une présentation non vide. Les références inconnues et relations affichées incomplètes restent des erreurs. Les objets globaux hors diagramme sélectionné sont exclus sans bruit et ne doivent pas être fusionnés. Les variantes de tests sont dérivées en mémoire ; ne pas présenter des exemples synthétiques comme enregistrés par l’application.
- Le modèle commun n’est pas une copie exacte du XML ; styles et positions ne sont pas conservés. Les flèches d’association PlantUML perdent leur direction. Signaler les ambiguïtés et pertes réellement détectées, sans promettre une conversion parfaite. Toute observation d’audit reste qualifiée et ne s’extrapole pas à tout le format SIMP.
- La lecture enrichie accepte les profils observés 10 et 12.75 ; les autres versions numériques sont signalées comme non validées. Ne jamais assimiler « tout type sélectionnable » à « toutes fonctionnalités traduites ». Activités : approximation par graphe d’états. Familles sans adaptateur : graphe générique annoté avec avertissement. Le XML archivé en commentaires JSON ne compte pas comme une traduction sémantique. Maintenir la matrice et les limites du README ; ne pas promettre de relire les sorties enrichies avec le parseur PlantUML strict.
- Ne jamais écraser la source ni une sortie existante. Ne pas exécuter de préprocesseur PlantUML, inclure ni charger de fichiers externes. Rejeter DTD et entités XML. Protéger les exports utilisateur ; ne pas déplacer ou modifier `Classdiagram1.svg` ni autres résultats utilisateur. Les résultats générés archivés, lorsqu’ils existent, résident dans `examples/validation/`.
- Ne pas redistribuer la fixture réelle ni les exports utilisateur. Les tests réels ou dépendant de données absentes doivent être ignorés uniquement lorsque les données sont absentes localement ; ne pas supprimer les données locales.

## Tests, packaging et documentation
- Respecter explicitement toute consigne de ne lancer aucun test. Sinon, privilégier les tests ciblés SIMP puis CLI/PlantUML ; ne pas figer le nombre de tests, ne pas mettre en place de cascade d’agents et ne pas relancer répétitivement les suites complètes. Au plus une validation complète utile après les tests ciblés.
- `tests/test_simp_views.py` : fixtures synthétiques et vérification optionnelle par le moteur officiel avec `PLANTUML_JAR`. `SIMP_REFERENCE_FILE` désigne un projet réel local, jamais redistribué ; son export `--all` est rendu en SVG si le JAR est fourni. Les références textuelles sont échappées pour empêcher directives, fonctions du préprocesseur et chargements d’images/liens. Tester aussi les nouveaux chemins enrichis, pas seulement les dataclasses historiques.
- Packaging natif : consulter `tools/build-native.py`, `packaging/rpm/` et `packaging/debian/` avant tout changement ; ne pas inventer d’options ni d’exigences de distribution. La construction Debian exige une adresse de mainteneur réelle fournie par l’utilisateur ; ne jamais publier d’adresse factice ni inventer mail ou URL d’auteur.
- Commandes usuelles : installation de développement `.venv/bin/python -m pip install -r requirements-dev.txt` ; CLI `.venv/bin/python -m simp2puml fichier.simp` ; tests ciblés `.venv/bin/python -m pytest -q tests/test_simp.py` (ou `test_puml.py`, `test_cli.py`, `test_atelier.py` ; ce dernier valide aussi avec `atelier-diagrammes check` si `ATELIER_DIAGRAMMES_BIN` ou le `PATH` le fournit). Voir `README.md` pour installation utilisateur, wheel et paquets natifs.
- Modèle selon la complexité, progression Luna → Terra → Sol ; pas d’Astra par défaut. IDs : `openai-subscribed/gpt-6-luna`, `openai-subscribed/gpt-6.1-terra`, `openai-subscribed/gpt-6.1-sol`.
