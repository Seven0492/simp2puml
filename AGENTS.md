# Consignes pour les agents

## Architecture et API
- Le paquet installable réside dans `src/simp2puml/` : `model.py` définit le modèle commun et ses invariants ; `cli.py` orchestre la CLI ; `puml.py` et `simp.py` sont des implémentations disjointes des deux formats. API directe : `from simp2puml.puml import parse_puml, write_puml` et `from simp2puml.simp import parse_simp, write_simp`. `parse_simp(text, diagram=None)` ; les erreurs sont `ConversionError` (`simp2puml.model`) et les avertissements/pertes détectées figurent dans `UMLDiagram.warnings`.
- Les points d’entrée sont `simp2puml` et `python -m simp2puml`. `main.py` à la racine reste un wrapper de compatibilité, pas l’implémentation de la CLI. Version : `0.1.0`, définie dans `simp2puml.__init__` et utilisée par le paquet ; ne pas la dupliquer ou inventer d’autres sources de vérité.
- Responsabilités séparées : modèle commun, orchestration CLI et adaptateurs de formats. Runtime bibliothèque standard, Python ≥ 3.11 ; `pytest` et outils de construction sont des dépendances de développement uniquement. Dépendances de construction/distribution selon `pyproject.toml` et `requirements-dev.txt`.

## Invariants du modèle
- Identités internes distinctes des noms affichés ; les classes homonymes restent distinctes. `UMLClass.kind` vaut `class`, `interface`, `enumeration` ou `interface_symbol` ; seules les énumérations ont des `literals` ordonnées. Une interface-symbol est un classifieur distinct sans membres ni modificateurs et cible des connecteurs fournis. Notes : identité `id`, texte brut `text`, références `targets`. Ne jamais inventer une identité ou résoudre arbitrairement une référence de type ambiguë.
- Pour l’héritage, `source` est l’enfant et `target` le parent. Les relations normalisées gardent la source à gauche et la cible à droite ; en composition, `source` est le tout. Préserver rôles, visibilités et multiplicités d’extrémité quand présents.

## Fidélité et sécurité
- Le profil SIMP est expérimental. Ne pas déduire la version de l’application de l’XML `12.75`, ni annoncer une compatibilité sans vérification dans l’application cible. La génération de structures/types textuels et `visibility` reste à valider. Ne pas assimiler nombre d’avertissements et nombre d’éléments perdus.
- `Monopoly.simp` à la racine est une fixture réelle protégée : ne jamais la modifier ni la redistribuer. Elle contient une généralisation sans origine, omissible avec avertissement seulement si l’autre extrémité existe, qu’elle n’est référencée nulle part et que le diagramme a une présentation non vide. Les références inconnues et relations affichées incomplètes restent des erreurs. Les objets globaux hors diagramme sélectionné sont exclus sans bruit et ne doivent pas être fusionnés. Les variantes de tests sont dérivées en mémoire ; ne pas présenter des exemples synthétiques comme enregistrés par l’application.
- Le modèle commun n’est pas une copie exacte du XML ; styles et positions ne sont pas conservés. Les flèches d’association PlantUML perdent leur direction. Signaler les ambiguïtés et pertes réellement détectées, sans promettre une conversion parfaite. Toute observation d’audit reste qualifiée et ne s’extrapole pas à tout le format SIMP.
- Ne jamais écraser la source ni une sortie existante. Ne pas exécuter de préprocesseur PlantUML, inclure ni charger de fichiers externes. Rejeter DTD et entités XML. Protéger les exports utilisateur ; ne pas déplacer ou modifier `Classdiagram1.svg` ni autres résultats utilisateur. Les résultats générés archivés, lorsqu’ils existent, résident dans `examples/validation/`.
- Ne pas redistribuer la fixture réelle ni les exports utilisateur. Les tests réels ou dépendant de données absentes doivent être ignorés uniquement lorsque les données sont absentes localement ; ne pas supprimer les données locales.

## Tests, packaging et documentation
- Respecter explicitement toute consigne de ne lancer aucun test. Sinon, privilégier les tests ciblés SIMP puis CLI/PlantUML ; ne pas figer le nombre de tests, ne pas mettre en place de cascade d’agents et ne pas relancer répétitivement les suites complètes. Au plus une validation complète utile après les tests ciblés.
- Packaging natif : consulter `tools/build-native.py`, `packaging/rpm/` et `packaging/debian/` avant tout changement ; ne pas inventer d’options ni d’exigences de distribution. La construction Debian exige une adresse de mainteneur réelle fournie par l’utilisateur ; ne jamais publier d’adresse factice ni inventer mail ou URL d’auteur.
- Commandes usuelles : installation de développement `.venv/bin/python -m pip install -r requirements-dev.txt` ; CLI `.venv/bin/python -m simp2puml fichier.simp` ; tests ciblés `.venv/bin/python -m pytest -q tests/test_simp.py` (ou `test_puml.py`, `test_cli.py`). Voir `README.md` pour installation utilisateur, wheel et paquets natifs.
- Modèle selon la complexité, progression Luna → Terra → Sol ; pas d’Astra par défaut. IDs : `openai-subscribed/gpt-6-luna`, `openai-subscribed/gpt-6.1-terra`, `openai-subscribed/gpt-6.1-sol`.
